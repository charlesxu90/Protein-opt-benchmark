  What "follow the original" actually means

  The upstream is two binaries used together:

  1. mu-former/main.py — a Trainer that takes a TSV of (mutation, fitness) rows
  and trains an encoder-decoder ensemble. Designed for offline supervised
  training on labelled data.
  2. mu-search/examples/baseline.py — a FLEXS fork. It wraps a trained µFormer
  as flexs.landscapes.MuformerLandscape (the proxy oracle), then runs a FLEXS
  explorer (e.g. AdaLead) which queries the proxy and the real oracle in
  batches.

  So in the paper's workflow: train µFormer offline → µSearch uses it as proxy →
  real oracle is queried in bursts.

  The unavoidable design question

  Our protocol is 96 oracle queries × 5 rounds. The upstream paper does not
  define this iterative regime. To "follow the original as much as possible" I
  see two faithful interpretations and need your call:

❯ MCTS only explores 4 sites, why it is still so slow?                          

● Great question — let me explain the actual bottleneck:

  Why "4 sites" is misleading for EvoPlay's cost

  EvoPlay's runtime isn't proportional to the search space size (20⁴ = 160k
  variants) — it's proportional to the number of MCTS rollouts × per-rollout 
  cost.

  Per seed at default config:
  - 480 target sequences to discover (96 × 5 rounds)
  - Each new sequence requires 1 MCTS episode
  - Each episode: ~30 playouts (n_playout=30 for seq_len ≤ 50)
  - Each playout: 4 actions × ~5-10 ms each

  Total per seed: ~480 × 30 × ~10ms = ~150 sec for MCTS alone — matches 
  observation (~10s/batch on GB1).

  But per playout has many small operations:

  ┌────────────────────────┬────────────────────┬──────────────────────────┐
  │          Step          │        What        │           Cost           │
  ├────────────────────────┼────────────────────┼──────────────────────────┤
  │                        │ Tiny network on    │ ~5ms (Python overhead    │
  │ 1. PVN forward pass    │ CPU                │ dominates the tiny       │
  │                        │                    │ matmul)                  │
  ├────────────────────────┼────────────────────┼──────────────────────────┤
  │ 2. Tree traversal      │ Python dict UCB-1  │ ~1ms                     │
  │                        │ walk               │                          │
  ├────────────────────────┼────────────────────┼──────────────────────────┤
  │ 3. GP predictor        │ sklearn GP on ~400 │ ~5-10ms (O(n²) per call) │
  │ evaluation at leaf     │  labels            │                          │
  ├────────────────────────┼────────────────────┼──────────────────────────┤
  │ 4. GP retraining each  │ sklearn GP fit on  │ O(n³) ≈ 50ms→5s per      │
  │ batch                  │ (96 → 480) labels  │ refit, × 480 refits      │
  ├────────────────────────┼────────────────────┼──────────────────────────┤
  │ 5. Policy-Value        │ Tiny network, but  │ ~5ms                     │
  │ Network gradient step  │ in Python          │                          │
  └────────────────────────┴────────────────────┴──────────────────────────┘

  The real culprits

  1. Python overhead — every operation, no matter how small, pays the Python
  interpreter tax. EvoPlay's MCTS is implemented in pure Python with dict nodes.
  ~10-20× slower than a C++ MCTS.
  2. GP retraining every batch — sklearn's GaussianProcessRegressor.fit() is
  O(n³) and single-threaded. By round 5, n=384, each refit is ~1-2 seconds. Over
  480 batches, this dominates.
  3. GPU is wasted — the PVN is so small that the Python→CUDA→Python round-trip
  is slower than just running on CPU. GPU at 0%.
  4. Search space size is irrelevant because MCTS doesn't enumerate — it samples
  paths through the tree. Whether the alphabet is 4 chars or 20⁴⁰⁰ chars, each
  playout costs roughly the same.

  Comparison to other methods on the same 4-site problem

  ┌─────────────────┬────────────┬─────────────────────────────────────────┐
  │     Method      │ per-seed   │                   Why                   │
  │                 │    time    │                                         │
  ├─────────────────┼────────────┼─────────────────────────────────────────┤
  │ MULTIevolve     │ ~30 sec    │ One sklearn Ridge fit per round, ~140k  │
  │ (Ridge)         │            │ predictions vectorized                  │
  ├─────────────────┼────────────┼─────────────────────────────────────────┤
  │ EVOLVEpro (RF)  │ ~10 min    │ RandomForest fit + predict on 140k      │
  │                 │            │ embeddings each round                   │
  ├─────────────────┼────────────┼─────────────────────────────────────────┤
  │ AlphaVariant    │ ~5 min     │ Small transformer + smart sampling, all │
  │                 │            │  vectorized                             │
  ├─────────────────┼────────────┼─────────────────────────────────────────┤
  │ EvoPlay         │ ~80 min    │ 480 batches × per-batch tree traversal  │
  │                 │            │ + GP refit                              │
  └─────────────────┴────────────┴─────────────────────────────────────────┘

  EvoPlay is ~150× slower than MULTIevolve on the same task because the per-step
  Python+sklearn overhead in MCTS dominates everything else. Reducing n_playout
  from 30 to 5 would give ~6× speedup; the GP refit cost would still be the
  floor.
